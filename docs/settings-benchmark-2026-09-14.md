# Paseo 설정 화면 전수 조사 및 설정 도입 검토 보고서

- 날짜: 2026-09-14
- 방법: 열려 있는 Paseo 데스크톱(v0.8.0, 호스트 ip-192-168-40-34…) 설정 화면의 21개 메뉴를 하나하나 열어 항목을 수집하고, 저장 값은 `~/Library/Application Support/Paseo/desktop-settings.json`과 렌더러 로컬 저장소(app-settings)로 교차 확인. 우리 앱의 현재 설정은 저장소 전수 조사로 병행. 이후 상반된 성향의 에이전트 2명(제품/UX vs 파워유저/엔지니어링)이 병렬 제안 → 교차 반박 → 수렴하는 커미티 토론으로 도입 후보를 추림.

## 2. 우리 앱 현재 설정

단일 스크롤 모달(탭 없음), 섹션 6개 — `packages/web/src/SettingsDialog.tsx`, 저장은 localStorage `colo-design.settings` 단일 키.

1. **화면**: 테마 갤러리 18종
2. **대화**: 모델 / 생각 시간(effort) / 확인 방식(permissionMode, 기본 bypassPermissions) / Claude가 화면 직접 확인 / PiP 표시 / 턴 끝나면 Claude 화면으로 / 생각 과정 보기
3. **동작**: 보내기 키(Enter·⌘Enter) / 실행 중 보내기(큐·끊고 보내기)
4. **GitHub**: PAT 등록(데몬 경유 OS 키체인)
5. **연결 레포**: 레포 주소
6. **문제 해결**: 온보딩 재실행 / 폴더 열기 / 업데이트 확인·설치 / 고급 폴드(접속 주소 재설정·지우기, 시스템 정보 읽기전용)

설정 밖 저장 상태: 레이아웃 너비·세션 이름·트리 접힘(같은 localStorage 키), 접속 주소·모델 캐시·알림 플래그(개별 키). 데몬: `~/.colo-design/config/projects.json`(프로젝트명·레포·baseBranch·명령 승인), 레포의 `colo-design.json`(install/check/build/preview 스크립트). 데스크톱: 자동 업데이트 확인 하드코딩(패키지드만, 15초 후, 24h 주기), 알림 항상 발생(토글 없음), 단축키·창 닫기 가드·dock 배지 고정.

## 3. 커미티 토론 결과 — 설정 도입 권고

구성: 제품/UX 전략가(이하 A)와 파워유저·엔지니어링 비평가(이하 B) 두 에이전트가 동일 자료로 병렬 제안(1라운드) → 서로의 제안을 교차 전달해 반박·수렴(2라운드). 양측 모두 저장소를 읽어 주장에 코드 근거를 붙였다(읽기 전용).

### 3.1 양측이 공유한 전제

- A: "Paseo의 설정은 *할 수 있는 것의 목록*, colonova의 설정은 *기획자가 스스로 고쳐야 할 문제의 목록*". 채택 기준은 "기획자가 한 달에 한 번이라도 스스로 조정하는 문제인가".
- B: 위 면도날은 취향 설정에는 정확하지만 보험성 설정을 놓치므로 보정 — "월 1회 조정 **또는** 사고 1건당 비용이 구현 비용을 초과하는가". "자리를 비운 사용자"를 위한 제품의 원격 루프(통지·가용성·복구·무손상 갱신)가 현재 전부 강제값이라는 설계 모순 지적(알림 무조건 발생 `main.ts:506-514`, 자동 업데이트 하드코딩 `main.ts:75-79`, 데몬 로그가 stdout에만 존재 `daemon/src/index.ts:148-150`, 데스크톱 데몬 spawn이 127.0.0.1 고정 `main.ts:45,325`). A가 2라운드에서 이 사실관계를 코드로 재검증해 인정.
- IA(정보구조): **단일 스크롤 유지 합의.** 탭 도입 기준 대신 운영 규칙 — 프로젝트 귀속 설정은 모달에 넣지 않는다, 그룹 8~9개·스크롤 3화면 초과 시 sticky 앵커 TOC로 완화.

### 3.2 최종 병합안 (A·B 수렴 + 의장 판정 2건)

**P0 — 코어 루프("보내놓고 자리 비움 → 복귀")의 신뢰성**

| # | 항목 | 형태 | 경위 |
|---|------|------|------|
| 1 | 데몬 회전 파일 로그 | 설정 없는 인프라(`~/.colo-design/logs/` 등, 예: 7일 보존) | B 주장, A 전향 수용. 데스크톱이 데몬을 spawn하므로 stdout은 사용자에게 존재하지 않음 |
| 2 | 권한 질문 알림 큐잉 | 질문이 대화를 막지 않고 알림으로 전달, 탭하면 해당 세션 복귀. **앱 내 가시 표시(세션 배지) 병행** — OS 알림이 거부된 환경의 조용한 멈춤 방지 | B 인프라 + A 프레임("물어보기 = 멈춤이 아니라 알림") |

| 7 | 종료 시 세션 질의 | 세션 실행 중 종료 시 "[백그라운드 계속] [종료]" + "이 선택 기억" 체크(Chrome 패턴), 트레이/메뉴바에 데몬 생존 표시 | B가 데몬 수명 토글을 철회하고 제안한 상호작용형 |

**의장 판정 1 (permissionMode 프리셀렉트): B 안 채택 — 프리셀렉트를 acceptEdits로.** 근거: 큐잉(2번)이 같은 변경 단위로 함께 배포되므로 A의 "조용한 멈춤" 우려는 앱 내 배지로 차단된다. bypass 기본 + 같은 키체인의 repo 스코프 PAT라는 현재 조합의 손실 반경이 1탭 마찰보다 크고, "아무도 본 적 없는 기본값 위험"을 없애는 것이 우선. 배포 1사이클 뒤 확인 카드 응답률·지원 티켓 데이터로 재검토하는 조건부. A의 온보딩 UI·일상어 프레임은 그대로 채택.

**의장 판정 2 (다른 기기 접속 등급): 기능(토큰 접속·리바인딩 동의·재발급)은 P0, QR 카드 UI는 P1로 유연.** 폰에서 장기 턴을 확인하는 것은 제품 가치 제안의 직접 완성이므로 기능 자체는 P0이지만, 자원이 부족하면 QR 카드만 한 단계 미뤄도 기능 목표는 달성된다.

### 3.3 토론 요약 — 어디서 갈렸고 어떻게 닫혔나

- **갈림의 축**: A는 "설정 개수를 늘리지 않고 문제의 목록만 채우자", B는 "강제값·부재 인프라가 지원 티켓으로 돌아온다". 2라운드에서 B가 4개 P0를 설정 노출 없는 형태(기본 동작·상호작용·인프라)로 재제출하면서 "원칙의 예외가 아니라 원칙의 완성"이라는 프레임으로 수렴.
- **서로가 굽힌 것**: B → 베타 채널 UI 철회, 단축키 재바인딩 철회(치트시트로 대체), 자동정리 토글→기본 동작, 데몬 수명 토글→종료 질의. A → 데몬 파일 로그·원격 접속 자격·업데이트 제어를 P0/조건부로 인정, 진단을 "복사 버튼"에서 "로그 전제"로 확장.
- **의장 판정으로 닫은 것**: permissionMode 프리셀렉트(acceptEdits), 다른 기기 접속 등급(기능 P0·QR 카드 P1).
