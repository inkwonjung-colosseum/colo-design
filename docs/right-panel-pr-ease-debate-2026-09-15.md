# 오른쪽 화면 영역 · 저장→넘기기(PR) 쉬워지기 — 커미티 토론 보고서

- 날짜: 2026-09-15
- 주제: Colo Design v0.3.6 작업트리 스냅샷 — (Q1) 오른쪽 화면 영역(미리보기+상단 바+저장·넘기기 패널)을 기획자 관점에서 더 끝내주게 만드는 것, (Q2) 비개발자의 "추가 수정 → 저장(커밋·푸시) → 넘기기(PR)" 8단계 경로를 제품 원칙(세 단어 어휘·main 불가·검토 게이트)을 지키며 줄이는 것.
- 방법: 상반된 렌즈 3인이 독립 제안(1차, 각 ≤5건) → 전원 기고문 교환·교차 반박(2차) → 수렴. 잔여 이견 5건은 의장 판정으로 마감. 읽기 전용(파일 미수정).
- 구성 비고: 에이전트 프로필 0개 → 커미티 스킬 폴백(프로바이더 디스커버리). A: claude/claude-opus-5(plan, 기획자 옹호), B: omp/zai/glm-5.2(write, 제품 엔지니어), C: omp/anthropic/claude-fable-5-1(write, PR 수신 개발자·협업 안전). 원문: `.claude/committee-right-panel-round{1,2}-{A,B,C}.md`, 팩트시트: `.claude/committee-right-panel-factsheet.md`.
- 증거: 소스 파일:줄 + README. 다른 에이전트가 동시 편집 중인 작업트리이므로 줄 번호는 스냅샷 기준. 사실 이견 교차검증 결과 **허위 주장 0건** — 3인이 서로의 인용을 재실측했고(2차 §4), 의장도 핵심 4건을 독립 재확인했다(§부록).

## 2. 만장일치로 닫힌 것 (의장 개입 불필요)

1. **게이트는 합치지 않는다.** DiffPanel의 저장 클릭(떠나는 단위 전체를 사람이 보는 유일한 자리 — runSave는 diff 전체를 승인 커밋), HandoffPanel의 제목·본문(기본값 문구가 그대로 PR이 되는 것 방지), 개발자 코멘트를 Claude에게 넘기기 전 읽기. C의 경계선 정의에 3인 전면 동의. `attachShots`가 DiffPanel이 보여 준 적 없는 커밋(SHOTS_COMMIT_MESSAGE)을 넘기기마다 만든다는 사실(repo.ts:1206-1242)이 자동 넘기기 기각의 결정타.
2. **체인의 조건**: `published`이고 그 순간 `delivery.actions.handoff.enabled === true`일 때만, 렌더마다 다시 읽은 값으로. A의 사실 정정 채택 — 조건은 "첫 사이클"이 아니라 "열린 넘김 없음"이며 병합될 때마다 재개된다(ensureCycleBranch가 merged 넘김을 지운다, repo.ts:1075) → 사이클마다 1왕복 절약. B의 전제조건 채택 — 강조 판정 `primary: "save"|"handoff"|"check"|null`을 delivery.ts로 통합(바 3버튼·복도 버튼 4곳의 단일 원천).
3. **선예열 트리거**: 요약은 턴 종료 후 새 턴 없이 ~20초(diff 해시 캐시 특성 — A 조임), 초안은 `저장됨` 칩 도달 + 복도 진입(B-5+A 시너지). 체인과 한 PR.
4. **A-3은 최소안으로 수렴**: A가 `수정 N번`(턴 수)을 자진 철회 — 되돌리기·최신화에서 카운터가 pendingChanges와 반대로 드리프트(증명 못 하는 숫자는 나침반에 못 올린다). 파일 수는 DiffPanel `자세히 보기 (파일 N개)`에만 남고, 사이드바 배지 `변경 N`은 제외(다른 일을 하는 다른 표면).
5. **B-2(전후 대조 PNG·v14)는 갈아넣는다**: '고치기 전' 그림은 핀이 찍는 순간의 크롭(C4 결정)으로 이미 무료 — 전체 화면이 아니라 기획자가 지목한 바로 그 사각형. A-4 최소안(턴 종료 토스트를 N행 + 핀 크롭)이 값을 프로토콜 0줄로 가져간다.

## 3. 의장 판정 — 잔여 이견 5건

**판정 1 (병합 착지의 시점): 착지는 "명시적 상태 확인 클릭" 또는 "다음 저장의 머리(runSave 진입 가드)"에서만. 조용한 트리거의 peek는 절대 착지하지 않는다.**
B(자동 착지 옹호)의 논리와 A·C(사람 있는 자리)의 논리를 이렇게 접는다. B 자신의 발견이 판정 근거다 — peek가 merged/closed를 칩에 수동 반영하면서 착지를 미루면 `this.branch`가 살아 있어 다음 저장이 **머지된 브랜치에 푸시**된다(ensureCycleBranch, repo.ts:1050-1053). 그렇다고 착지를 사람 없는 타이머에 맡기면 되돌리기 기록이 조용히 지워진다(A — repo.ts:1284-1286, README:298-299). 둘 다 막는 자리는 하나다: **runSave 진입에서 peek → merged면 오늘의 merged 착지를, closed면 아래 판정 2의 랜딩을 수행한 뒤 새 브랜치**. 저장 버튼은 사람이 누른다 — "사람 있는 자리" 조건이 성립하고, C의 "가드가 본체·타이머는 앞당김" 구조가 된다. 조용한 peek는 open↔changes_requested 칩 이동과 알림 문구까지만(B 규칙 채택).

**판정 2 (C-3 랜딩의 형태): B 수정안 채택 — closed 랜딩은 merged 랜딩과 같은 형태(fetch → dirty면 checkout만, clean이면 checkout+reset) + 체크포인트 유지.**
C 원안(`setCycle(null)`만, 워크트리 그대로)은 ensureCycleBranch의 암묵 계약을 깬다: 새 사이클 브랜치는 `checkout -B`로 **현재 HEAD에서** 만들어지므로(repo.ts:1070), 반려된 팁 위에서 다음 저장은 반려된 커밋들을 그대로 다시 제안하는 새 PR을 연다 — C-3이 막으려던 것과 똑같은 부활. 수정안은 dirty 시 미저장 작업을 base 위에 보존하므로 "반려 뒤 계속 고치기"도 산다. closed 행은 merged 행을 미러(unsaved면 저장 열림·넘기기 잠김·상태 확인 강조), 체크포인트는 유지(반려 작업은 되감을 가치가 있다). 저장 기록 드로어는 비지만 반려 작업은 닫힌 PR·원격 브랜치·체크포인트로 도달 가능 — 손실 없음. A의 격상(영향 3→4)과 사실 정정(closed가 updatePullRequest 덮어쓰기의 유일한 도달 경로 — C-2와 C-3은 같은 전선)을 함께 기록한다.

**판정 3 (전수 훑기): Phase 2 하나의 묶음으로 — 요청 시 훑기 + 넘기기 캡처 미리보기가 캡처 세트를 공유. 지금은 매트릭스+본 곳 표식만.**
A의 세 조건(명시 버튼·시각 표기·자가 무효화 흐려짐)과 "이 파이프라인은 오늘 이미 매 넘기기마다 동의 없이 돈다 — 온디맨드가 비싸면 넘기기 뒤에서 돌리기엔 더 비싸다" 논지, C의 "캡처는 증거이므로 게이트(HandoffPanel)에" 논지, B의 lazy·턴 중 잠금 조건이 전부 양립한다: 훑은 세트를 (그 뒤로 안 바뀌었으면) 넘기기가 재사용 — 총 캡처 횟수는 오늘과 같거나 적고, "아무도 안 본 스크린샷"이 "기획자가 확인한 스크린샷"이 되며 C-5(b) 고지 문장이 동의로 승격한다. PNG 전송이 v14 범프를 요구하므로(B) 별도 PR. 순서 이견(A 2위 vs B Phase 2)은 PNG 경로가 필요한 만큼 의장이 Phase 2로 끊는다 — 매트릭스+표식이 이미 커버리지 질문의 1차 답이다.

**판정 4 (타이머·알림): 데몬 타이머 10분(활성 프로젝트·열린 넘김·턴 idle)을 기본 패키지에 넣고, 상태가 바뀔 때만 OS 알림 1회.**
교차 양보가 성립했다 — B는 "폴링이 아니다"를 인정해 웹측 폴링을 철회하고 데몬 배치·repo.status 방송(프로토콜 0줄)을 제시했고, A는 2차에서 그 배치를 "내 안보다 낫다"며 채택했다. B가 기본 패키지에서 뺀 유일한 이유는 A의 반대였는데 A가 철회했으므로 남는 반대는 없다. 알림은 B의 증명대로 배경 읽기 없이는 원리적으로 불가(포커스 엣지는 사람이 이미 들춘 뒤) — 타이머가 있어야만 산다. 조건: README:293 "폴링 없음" 문장과의 정합을 이 문서로 기록한다(그 문장은 변경 건수 트리거에 관한 것이었고, 상태 폴링은 새 결정이다 — D83 번복 전례와 같은 등급).

**판정 5 (C-2 데몬 절반): 메모 한 줄 코멘트는 PR-3에 실는다. reviewIds·handled 이전·인라인 답글은 v14 묶음으로.**
B의 보류 사유가 둘인데 둘 다 지금 닫힌다: (1) "원칙 3 기록이 필요" — 아래 §4-1이 그 기록이다. (2) "저장마다 GitHub 쓰기 증가" — 열린 넘김이 있을 때만·저장 1건당 1줄·레포 설정 `notify: false` 탈출구로 상한이 묶인다. A의 비용 3 산정은 handled 이전(localStorage→데몬)에 묶여 있었는데 그 부분은 v14로 갔으니 메모 줄의 한 줄은 비용 1이다. C의 바닥("PR 열린 뒤 저장이 GitHub에 아무 말도 안 하는" 상태는 남기지 않는다)은 커미티 수렴의 요건이고, C 자신의 2차 안("범프 전에는 메모 한 줄만")과 정확히 같은 모양이다. 웹 절반(강등·라벨·읽기 게이트)은 3인 만장일치로 라이더행.

## 4. 결정 기록 (이 문서가 기록이다)

1. **원칙 3 확장 해석 — 저장은 기획자의 확정 발화다**: 열린 넘김(open·changes_requested)이 있는 동안의 저장은 그 메모를 PR 스레드에 한 줄로 남긴다(사람이 저장 검토에서 본 메모 그대로). 레포 설정 `notify: false`로 끌 수 있다. 저장의 "퇴장 허가"에 개발자를 향한 이 한 줄이 포함됨을 기록한다.
2. **README:73 계약 변경 — 칩의 숫자**: `저장 안 함 N건`의 N(porcelain 파일 수)이 "저장하지 않은 작업 N건"으로 번역되어 온 것을 폐기하고 칩은 `저장 안 함`만 말한다. 파일 수는 저장 리뷰의 `자세히 보기 (파일 N개)`(DiffPanel)와 파괴적 버리기 확인(경로 나열)에만 남는다. 사이드바 배지 `변경 N`은 유지. 관련 스냅샷·e2e 갱신 동반.
3. **README:293 정합 — 제한된 상태 폴링**: 변경 건수는 여전히 세 트리거(폴링 없음). 넘긴 요청의 GitHub 상태는 데몬이 10분 간격(조건: 활성·열린 넘김·idle)으로 읽는다 — 칩은 기계 신호만(원칙 6)이라는 약속은 강화된다.
4. **C-1은 결정 변경**: handoff-draft.ts:11-15 주석이 명시한 "spec 없는 화면은 구멍 난 줄 대신 아예 빼기"를 폐기하고 "(기획서 없음)"으로 남긴다 + 이번 사이클에 커밋된 기획서를 `blob/<branch>/specs/…` 링크로(PR 본문은 개발자 표면 — 파일 경로 금지 원칙의 적용 밖, 기획자 표면엔 유출 금지).
5. **`summaryLines` 유령 prop 제거**: `<!-- colo-design:summary -->` 마커의 생산자·파서가 코드베이스에 없음을 3인 확인. 완성(모델 출력에 계약 거는 확률적 길)이 아니라 제거 — 데몬 `repo.summarize`는 해시 캐시로 결정적이다.
