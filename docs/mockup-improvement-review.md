# 목업 vs 실제 구현 — 개선점 토론 결과

> 작성일: 2026-09-16
> 방법: 분석가 4명(레일/채팅/프리뷰/모달)이 실제 코드(`packages/web/src`, `packages/desktop/src`)와 목업(`mockups/core`, `mockups/cycle`)을 대조 → 비평가 2명(제품/공학)이 판정 → 종합.
> 범위: 기존 기능 화면만. `mockups/ideas/`(신기능 제안)는 제외.

---

## 0. TL;DR

- **즉시 채택(CHEAP, 양 비평가 합의) 20건** — 대부분 문구·배치·상태 표시. 아래 §1.
- **조건부 채택 4건** — 요구는 맞지만 목업의 형태가 틀린 것. §2.
- **기각 3건** — 목업이 실제보다 나쁘거나, 코드에 명시된 불변식과 충돌. §3.
- **보류 4건** — 비용 대비 근거 부족 또는 데이터 파이프라인 부재. §4.
- **⚠️ 판정**: 분석가들이 올린 "목업이 나쁜 점" ~20건은 두 비평가 모두 **전부 실제 구현 우위**로 확인. 목업에서 그대로 가져올 것은 없고, 가져올 건 전부 "형태를 바꿔" 가져온다.
- **체계적 발견**: 실제 UI의 가장 큰 단일 문제는 개별 요소가 아니라 **"정보가 hover tooltip 뒤에 있다"는 패턴이 7개 표면에서 반복**된다는 것. §5.

## 2. 조건부 채택 — 요구는 맞고 형태는 틀림

| 개선 | 판정 |
|---|---|
| **사이클 진행 레일** | 제품 #1 vs 공학 기각 권고 — `delivery.ts:4-5` "스테퍼의 다섯 단계 레일은 지워졌다" 의도적 삭제. **요구(흐름 교육)는 채택, 번호 스테퍼 형태는 기각.** 기존 상태 칩+`delivery.next.line` 팝오버를 강화하는 방향(다음 단계가 뭔지 항상 말하게). 목업 번호가 3부터 시작하는 것도 목업 버그. |
| **도구 행별 파일명** | `activity.tsx:11-13` "A planner never asked for a tool log" — 여덟 줄 벽의 교훈으로 합산이 의도적. **합산 줄 유지, 펼침 내부에만 행별 파일명.** |
| **개발자 코멘트 본문 상시** | `ScreenPanel.tsx:1560-1571` 읽기 게이트("모두 AI에게"는 각 코멘트를 펼쳐 읽은 뒤에만 열림)와 충돌. 본문 상시화 시 게이트 재설계 필요 — 처리됨은 접기 기본값으로 절충 가능하나 재설계 선행. |
| **화면 목록 매트릭스** | 데이터는 전부 있음(cellSeen·unseenOnly) MEDIUM이나, 화면 수십 개×상태 다수면 고정 격자 파열 — 가로 스크롤/행 접기 설계 선행. 제품 측도 "안 본 상태"가 새 정신 모형이라 보류 의견. **프로토타입 후 판단.** |

## 3. 기각 — 실제가 나음

- **우측 정렬 말풍선**: ❯ 로그 미학은 "채팅이 아니라 세션 로그"라는 의도된 정체성(styles.css:1330-1377). 채팅 앱 흉내는 '세션' 성격을 흐림.
- **프로젝트 섹션 레이블**: 트리가 프로젝트 목록인 건 자명, 데드 웨이트.
- **'저장할 변경 N개' 카운트**: `delivery.ts:208-210` — 핀 하나가 파일 셋을 건드려 숫자가 체감과 역상관, 이미 겪고 버린 함정. 재도입 금지.

## 4. 보류 — 비용/근거 문제

- **scard 썸네일 카드**: 와이어 썸네일 생성·저장·프로토콜 경로 없음(EXPENSIVE). 썸네일 없이 제목+route+상태 칩 나열(MEDIUM)은 별도 검토 가치 있음 — "다른 상태도 보기" 진입점.
- **보낸 그림 기록**: `block.images`는 개수뿐, `thumbs`는 live-echo 전용·재생 시 없음 — 데몬/프로토콜 변경(EXPENSIVE).
- **알림 사건×채널**: settings 스키마+desktop bridge+메인 프로세스 3층 변경(EXPENSIVE). 가치는 인정 — 단 "확인이 필요하면→끔"은 절대 금지(허가 요청이 조용해지면 멈춘 줄 모름).
- **반영됨 인앱 토스트**: 토스트 인프라 없음(MEDIUM). 기존 `mergedFlash`(ScreenPanel.tsx:1045) 칩 플래시 강화로 절충 가능.
- **핀 스트립 미리보기 아래**: PinTray와 이중 표시 혼란 우려. `.pins` dead CSS(styles.css:5876-5920) 정리가 선행.
- **레포 목록 인라인 경고**: inspection은 pick 후에만 요청 — 캐시된 결과 있을 때만 배지로 절충.
- **톱바 대화 제목+⋯ 메뉴**: MEDIUM(스레드 제목 플러밍+메뉴 추출). 가치 있으나 우선순위는 아래.

## 5. 체계적 발견 — 개별 항목보다 중요

1. **hover-tooltip 의존이 체계적 결함**: 항상 허용 범위·더 보기 설명·잠긴 버튼 이유·제안 칩 의미·Enter 힌트·컨텍스트 %·핀 해제 — 7개 표면에서 동일 패턴. 개별 수정이 아니라 원칙 선언이 필요: **"행동 옆 설명은 인라인, 상태 표지는 사건 시에만."**
2. **'기다림'의 언어 부재**: 정리 중·확인 중·작업 중·주소 대기 — 4곳 모두 "멈춰 보임"이 공통 원인. **동사+경과초("~하는 중 · N초")를 앱 전역 패턴으로.**
3. **사이클 종착 신호 체인의 구멍**: 넘기기→개발자 확인→반영 사이에 기획자가 보는 중간 상태 언어가 없음 — "기다리는 중" 표현이 어디에도 정의되지 않음.
4. **파괴 확인의 비대칭**: 대화 삭제엔 '남는 것' 명시를 채택하면서 변경 버리기엔 ±수만 — **모든 파괴 확인에 "남는 것" 한 줄 규칙** 적용 권장.

## 6. 제안 순서 (PR 단위)

1. **PR-A 레일 발견성**: 상시 ＋·검색 아이콘·leaf--add 상시. (CHEAP×3)
2. **PR-B 컴포저·테이프 안내**: 힌트 줄·다음: 접두·컨텍스트 숫자·첨부 placeholder·정리 중 줄·진행 시계·요약 경계·허가 카드 라벨. (CHEAP×8, 같은 파일군)
3. **PR-C 프리뷰 표면**: 상태 칩 전용 줄·오류 띠 이동·빈 스테이지·대기 중 잠긴 버튼·멈춤 카드 문구·더 보기 설명·핀 해제 힌트. (CHEAP×6+멈춤 카드 재구조 MEDIUM)
4. **PR-D 모달·확인**: modal__foot·버리기 태그/±·삭제 문구·넘기기 pill·기록 '지금 상태'. (CHEAP 묶음)
5. **PR-E 설정·온보딩**: 저장 위치·외부 이동 예고·확인 중 행·레포 경고(캐시 절충). (CHEAP×3+MEDIUM×1)
6. **이후 별도 검토**: 사이클 흐름 교육(팝오버 강화)·코멘트 게이트 재설계·매트릭스 프로토타입·알림 개편·토스트·scard 상태 칩·보낸 그림 영속.
