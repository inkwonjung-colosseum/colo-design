# 토론 브리프 — 이 구조가 그 여정에 최적인가

## 심문 대상: 최종안 구조
`docs/layout-redesign-synthesis.md` §4의 권고 구성. 요약:
- 앱은 두 얼굴: 「지금」 피드 홈(나를 기다리는 일: 확인 대기/개발자 코멘트/치워둔 작업/진행 중/지난 일) ↔ 작업 모드(현행 3열: 레일 | 대화 | 미리보기)
- 레일 존치, 최상단에 「지금」 진입 행+배지
- 사이클 칩·저장·넘기기는 프로젝트 전역, 미리보기 바에 표시
- 허가 승인은 대화 안에서만(카드는 "대화에서 보기"까지)
- 홈은 일이 있을 때만 현관; 없으면 마지막 대화 복원
- 미리보기 몸통화는 보류(실측 게이트)

목업: `mockups/layout/final.html`(전환 동작함), 근거: `docs/layout-redesign-synthesis.md`, 원 제안들: `docs/layout-proposals/`

## 심문 기준: 이 여정
비개발자(기획자·디자이너)가
1. 개발자의 레포를 연결하고
2. 채팅(말+그림)으로 화면을 만들고 고치고
3. 저장하고 개발자에게 넘기고
4. 개발자의 검토·변경 요청·반영을 받아 다음 사이클로 간다

이 여정의 **각 단계에서** 이 구조가 최적인가? 특히:
- 단계 1(연결): 온보딩 게이트 → 레포 선택 → 「지금」 홈의 빈 상태가 첫 화면. 이 흐름이 맞나?
- 단계 2(만들기): 대화+미리보기 2열이 작업 모드. 핀·계획 카드·실행 중 보내기가 이 구조에서 잘 사나?
- 단계 3(저장·넘기기): 프로젝트 전역 칩+미리보기 바 액션. 비개발자가 "저장=이 대화의 결과 묶기"가 아니라 "프로젝트 전체 누적"임을 이 구조가 가르치나?
- 단계 4(검토 루프): 개발자 코멘트 도착 → 「지금」 카드 → 대화로. 변경 요청을 고쳐 다시 넘기는 루프가 자연스러운가?
- **매일의 리듬**: 이 사용자의 하루는 "아침에 열어 밤새 돌던 것 확인 → 지시 → 퇴근"이다. 이 구조가 그 리듬에 맞나?

## 당신의 과제
1. **판정** — 이 구조가 이 여정에 최적인가? 예/아니오/조건부, 한 문장.
2. **여정별 심문** — 위 4단계+리듬 각각에서 이 구조가 돕는 것/방해하는 것. 구체적 화면 요소를 들 것.
3. **가장 약한 고리** — 이 구조가 이 여정을 망가뜨릴 수 있는 지점 하나. "왜 다른 안이 이걸 더 잘 푸나"까지.
4. **놓친 대안** — 4개 제안(A~D)과 최종안 밖에 있는, 이 여정에 더 맞는 구조가 있다면 스케치. 없다면 왜 없는지.
5. **한 가지 수정** — 최종안에 딱 하나만 고칠 수 있다면.

근거는 코드(`packages/web/src`, `packages/protocol/src`)와 문서(`docs/`, `README.md`)에서 가져와라. 목업 파일을 읽어도 된다. 마크다운으로 반환, 파일 쓰지 마라.
