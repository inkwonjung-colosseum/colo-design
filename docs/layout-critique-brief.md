# 화면 구성안 교차 비평 브리프

읽을 것: `docs/layout-brief.md`(원 과제), 그리고 네 개의 제안
- `docs/layout-proposals/A-sonnet-attention-board.md` — "주의 보드" 홈(4열 칸반) + 대화 드로어. 카드=스레드, 열=세션 상태(확인 필요/진행 중/새 답 옴/다 봄). 사이클 칩은 프로젝트 전역 1개로 승격.
- `docs/layout-proposals/B-glm53-two-rooms.md` — 창이 두 개의 방: 「지금」(기다리는 일 피드, 창 전체) ↔ 「작업대」(머리줄 + 대화|미리보기 2열). 레일 전체 폐기.
- `docs/layout-proposals/C-glmflash-stage-body.md` — 미리보기를 몸통(1fr)으로, 대화를 오른쪽 날개(380px, 접힘)로. 레일 유지 + 상단에 '기다리는 것' 이벤트 줄. 데몬·프로토콜 변경 0건.
- `docs/layout-proposals/D-swe2-inbox-home.md` — 받은편지함이 홈(레일 최상단 고정 행), 작업 모드는 미리보기가 **도킹 패인**(화면 없으면 접힘). 사이클 칩·저장·넘기기를 스레드 헤더로 이동.

배경 제약(원 브리프 요약): 비개발자 대상, git 용어 금지, 한 번에 한 프로젝트 활성(웜 프리뷰 2개), 확인 요청은 언제나 옴, 사이클 스테퍼 부활 금지(`delivery.ts`에 의도적 삭제 기록), 저장/넘기기는 **프로젝트 단위**지 화면·대화 단위가 아님, 미리보기는 화면의 유일한 문.

## 당신의 과제
네 안을 **채택 가능한 하나의 구성**으로 만들기 위한 판정을 내려라. 형식:

1. **순위와 이유** — A/B/C/D 순위. 각 한 줄 근거.
2. **치명상** — 각 안이 가진, 고치지 않으면 제품을 망가뜨릴 결함 1개씩. 코드/데이터 계약 근거를 들 것(`packages/web/src`, `packages/protocol/src` 확인 가능).
3. **합성 가능 조각** — 안을 통째로 고르지 말고, 서로 결합 가능한 조각과 **양립 불가능한 조각**을 구분하라. 특히: (a) 홈의 형태(칸반 vs 피드 vs 레일 최상단 행), (b) 레일 존치 여부, (c) 미리보기의 위치·기본 가시성, (d) 사이클 칩의 소유자(프로젝트 전역 vs 스레드 헤더 vs 미리보기 바).
4. **당신의 판정** — 하나의 권고 구성. ASCII 한 장. "왜 다른 조합이 아닌가"를 2~3줄.
5. **단계적 도입** — 지금 코드에서 가장 싸게 검증 가능한 첫 조각은 무엇인가. 되돌릴 수 있는 순서로 3단계.

간결하게. 모든 문장이 판단이어야 한다. 마크다운으로 반환하고 파일은 쓰지 마라.
