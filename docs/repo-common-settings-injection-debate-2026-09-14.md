# 레포 연결 시 공통 설정 주입(.agents/.claude) — 커미티 판정 보고서

- 날짜: 2026-09-14
- 주제: "레포를 연결하는 시점에 앱이 '공통 설정'을 연결 레포의 `.agents/`·`.claude/`에 넣어, 어떤 레포를 연결하든 에이전트가 잘 작동하게 만든다"는 접근의 평가.
- 방법: 상반된 성향의 에이전트 2명(제품/UX 전략가 A vs 파워유저·엔지니어링/보안 비평가 B)이 동일한 사실 팩트시트로 병렬 제안(1라운드) → 교차 반박(2라운드) → 수렴. 양측 모두 저장소를 읽어 주장에 코드 근거를 붙였다(읽기 전용). 잔여 이견은 의장 판정 2건으로 마감.
- 구성 비고: 에이전트 프로필이 0개여서 커미티 스킬의 폴백 규칙(프로바이더 디스커버리)로 위원을 구성했다 — A: claude/claude-opus-5(plan), B: zai/glm-5.3(omp, ask).

## 1. 판정: 원안 거부 (양측 만장일치)

목표("어떤 레포든 잘 작동")는 유효하다. 그러나 '공통 설정'의 종류마다 이미 올바른 계층이 이 코드베이스에 존재하고, 주입은 그중 유일하게 **기획자의 작업 데이터와 같은 공간(클론 작업트리)**을 골라 쓰는 안이다. 신뢰 경고 체계의 자기모순, 저장 파이프라인 오염, 버전 없는 드리프트 — 사고 1건당 비용이 구현 비용을 명확히 초과한다.

## 2. 근거 (양측, 코드 검증)

### 2.1 신뢰 모델 자기모순 — 결정타

- `repoSettingsWarning`(repo.ts:308-333)의 문구는 **"이 레포가 보낸 .claude/settings.json…"**. 앱이 같은 경로에 쓰면 출처 오귀속이다. 지문이 `sha256(root + raw bytes)`(repo.ts:331)라 앱이 쓴 바이트와 레포가 보낸 바이트를 구조적으로 구별할 수 없고, 공통 설정이 갱신될 때마다(바이트가 바뀔 때마다) 재경고가 발생한다.
- 회피용 "앱이 쓴 파일" 바이트 매칭은 악성 레포가 같은 바이트를 업스트림에 심어 경고를 우회하는 길이 된다(B).
- `trustWorkspace`(repo.ts:2957-2990)가 기획자 대신 신뢰를 누르는 정당성은 주석 한 문장 — *"grants nothing they did not ask for"*. 이는 **레포가 선언한 규칙의 발효**에만 성립한다. 앱이 스스로 규칙을 **창작**하는 순간 이 문장이 거짓이 된다. 발효와 창작은 다르다(A).

### 2.2 git 위생 — 취향이 아니라 기능 파손

- **저장 카드 오염**: `diff()`가 untracked를 added 훅으로 포함(repo.ts:433-434, 1015-1026) → 연결 직후, 화면 작업 전에도 설정 파일이 저장 리뷰에 등장. `refreshPendingChanges`(repo.ts:2803-2815)가 "저장 안 함" 칩을 점등.
- **되돌리기가 설정을 지운다**: `checkpointRestore`(repo.ts:1870-1913)는 스냅샷에 없던 미추적 파일을 `rmSync`로 삭제하고 `safeRepoPath`(repo.ts:585-594)는 점 디렉터리를 막지 않는다. `discardChanges`(repo.ts:1743-1747)의 "버리기"도 동일. 기획자가 화면 하나 되돌렸더니 에이전트 설정이 사라져 다음 턴부터 권한 카드가 쏟아지는, 원인 추적 불가능한 고장.
- **최신화 충돌**: `stashUnsavedWork`(repo.ts:2094-2105, `--include-untracked`) → 개발자가 자기 `.claude/settings.json`을 커밋해 오면 기획자에게 자기가 만진 적 없는 파일의 충돌 카드가 뜬다.
- **커밋 경로**: "승인된 경로만, `git add -A` 금지"(repo.ts:1104-1106) 정책과 만나면 플래너가 diff에서 설정 파일을 승인해 넣는 순간 앱 설정이 핸드오프 PR에 동승해 개발자 리뷰에서 거부된다 — 지원 티켓의 전형.

### 2.3 나머지 저장 위치도 전부 막힌다

커밋하면 앱 업데이트 하나가 연결된 **모든** 레포에 PR을 연다. `.gitignore`에 넣으면 소음은 사라지지만 개발자 체크아웃엔 파일이 없어 "어떤 레포든 잘 작동"이 **앱 안에서만 참**이 된다 — 협업 도구에서 목표의 포기.

### 2.4 `.agents/`는 죽은 디렉터리

저장소 전체 참조 0건. Claude Code는 `.claude/`만 읽는다. 읽는 주체 없는 디렉터리를 연결마다 만들면 기획자에겐 저장 카드 노이즈, 개발자에겐 "이게 뭐냐"는 PR 질문, 우리에겐 영구 하위호환 부채. 읽는 주체가 생기는 날 규격을 정의한다.

### 2.5 사실관계 정정 (양측 1라운드 오류 → 2라운드 합의)

- bootstrap은 '빈 레포'가 아니라 **`colo-design.json`이 없는 레포**에서만 준비 턴을 돈다(repo.ts:2262-2276; 트리거 `RepoPicker.tsx:219`의 `!hasColoDesign`). B의 "bootstrap이 이미 달성한다"는 발언은 철회.
- 그러나 **재실행 경로가 없다**: `bootstrapSlugs`는 `project.create`의 `message.bootstrap`에서만 채워지고(server.ts:1092), `project.update` 스키마엔 필드가 없다(protocol/index.ts:322-334). 한 번 계약이 생기면 다시 안 돈다. 남는 것은 커버리지 구멍이 아니라 **드리프트 구멍** — v0.3에 연결된 레포는 관례가 v0.3에 영구 고정된다. 원안이 풀려던 문제의 진짜 정체가 이것이므로, 이 구멍을 닫지 않으면 원안이 되살아난다(A).

**권한 번들 상세(2라운드 수렴안)**

- 구현 자리는 `managedSettings`뿐이다. `PermissionMemory` 확장은 금지 — `permissionSignature`는 정확 일치 서명(`Bash:command:<문자열 그대로>`, session.ts:137-147)이라 `npm run *` 류 번들을 표현할 수 없고, 글롭 매처를 새로 쓰면 CLI `permissions.allow` 의미론의 두 번째 구현이 되어 해석이 갈리는 날이 곧 보안 사고다(A).
- 가시성은 카드가 아니라 표시 계층에서 산다: SDK `resolveSettings()`가 출처(`'managed'` 포함)별 효력 권한을 읽어 주므로, **물어볼 때만 뜨는 카드와 달리 "사전 승인돼서 카드가 안 뜨는 것"까지 보여 주는 목록**이 가능하다(A). 이는 B가 요구한 가시성보다 강하다.
- 번들 내용은 미측정이다. `alwaysAllowed`가 세션 인스턴스 필드라(session.ts:295) 비영속이므로 기획자는 새 대화마다 같은 카드를 다시 받는다 — **그 반복 카드 로그부터 측정해 번들을 정한다**(A가 B에게 넘긴 열린 질문, 의장 판정 2에서 게이트로 채택).
- 실행계 도구(명령 실행 능력이 있는 것)가 하나라도 번들에 들어가는 순간 플래너 가시 선택(온보딩 카드)으로 승격 — B의 양보 불가 선.

**"연결 관례 최신화" 턴(양측 제안의 병합)**

- 검출: 관례 마커(브리지·래퍼 규칙 등)의 **부재 또는 낡음(버전 마커)**. 부재 검출은 B의 "관례는 첫 저장을 탄다"(부재 시 appendSystemPrompt로 "이 관례를 지켜 반영하라" 지시 → 첫 저장 PR에 동승), 낡음 해소는 A의 명시적 최신화 턴이 담당한다.
- 실행: 기획자가 눌러 시작. **쓰는 주체는 앱이 아니라 세션** — 현행 브리프로 레포를 갱신하는 한 턴이므로 신뢰 경고 체계와 충돌하지 않는다.
- 확정: 기존 저장→승인→PR 파이프라인 그대로. 재주입이 아니라 제안이고, 승인자는 개발자다. 2.5의 드리프트 구멍(v0.3 영구 고정)이 이 턴으로 닫힌다.

## 4. 토론 요약 — 어디서 갈렸고 어떻게 닫혔나

- **판정(거부)은 1라운드부터 양측 일치** — 갈림은 전부 대안의 형태에서였다.
- **갈림의 축**: 권한 번들의 가시성(비가시 정책 tier vs 카드 출처 표시), 공통 지침의 주인(앱 상수 vs 기획자 편집 필드), 스킬의 홈 tier 주입 정당성, bootstrap의 적용 범위(사실관계).
- **서로가 굽힌 것**: B → in-memory+카드 출처안 철회(최소 집합엔 과투자), 편집 가능 필드안 자체 기각("앱 갱신과 사용자 수정이 한 필드에서 충돌하면 내가 레포 주입에 주장한 것과 같은 드리프트 비용"), "어떤 레포든 bootstrap이 이미 달성" 발언 철회. A → `managedSettings` 비가시 안의 일관성 결함 인정(자신의 원안 거부 논리를 내 B안에 안 대었음), C안(주입 강행 시 방어선) 철회.
- **사실관계로 닫힌 것**: bootstrap 범위(2.5). 이 과정에서 원안의 동기 중 진짜 결함(재실행 없는 드리프트 구멍)이 분리되어 병합 권고의 "최신화 턴"으로 치환됐다.

**의장 판정 1 (공통 스킬의 미래 채널): 보류 유지, 미래 기본선은 A의 원칙.**
양측 모두 오늘 행동은 "선설치 없음"으로 일치하므로 남는 것은 미래 조건부 채널뿐이다. 스킬이 실제로 필요해지면 첫 후보는 **관례 최신화 턴에 동승하는 커밋된 스킬**(개발자 PR 리뷰)로 한다. 홈 tier(`~/.claude/skills/colo-design/`) 주입은 예외로만 재검토하며, 그 게이트는 B의 3조건(앱 이름공간·수정된 파일 덮어쓰기 금지·설치 공개)이다. 근거: 홈 주입은 git 밖이라 흔적·되돌림이 없고, `settingSources`가 사용자 tier를 싣는 이유를 적은 주석("터미널과 동일하게")을 앱이 스스로 깨뜨리며, 개발자의 터미널 세션까지 오염한다(A). B 역시 "예약 슬롯일 뿐"이라 부담을 이미 인정했다.

**의장 판정 2 (권한 번들 내용 결정 순서): 측정이 먼저다.**
번들 목록은 카드 반복 로그(`alwaysAllowed` 세션 비영속으로 인한 재발문)를 측정한 뒤 정한다. 실행계 도구 포함 시 플래너 가시 승격은 B의 양보 불가 선을 그대로 반영한다. "카드가 많다"는 아직 측정된 적 없는 문제다.

## 5. 의장 관찰 — 이미 존재하는 동의 기반 채널

권한의 레포 로컬 기록은 **이미 동의 기반으로 존재한다**: 기획자가 "항상 허용"으로 답하면 CLI가 제안하는 `addRules` 갱신이 `.claude/settings.local.json`으로 향한다(session.ts:952-956 주석). 즉 "카드 폭주"에 대한 1차 답은 앱이 저술하는 번들이 아니라, 이미 있는 카드 답변의 지속화(CLI 자체 제안)다. 앱 번들은 이 채널로 충분해 보이는 것의 잔여분일 뿐이며, 그래서 판정 2의 측정 게이트가 먼저다.
