## 공통 진단 — 지금 구조가 이 질문에 왜 부족한가

현재 3열+피드 홈은 **"이미 연결된 사람의 매일"**을 잘 담는다. 그런데 이 질문의 대상은 **여정의 처음**에 있다:

1. **토큰→레포 연결**이 온보딩 카드 한 줄("토큰 붙여넣기")에 압축돼 있다. 비개발자에게 토큰은 "어디서 구하는지, 왜 필요한지, 붙여넣으면 무슨 일이 생기는지" 전부가 낯설다. 가장 이탈률이 높은 지점이 가장 얕은 표면에 있다.
2. **저장→넘기기→반영**이 사이클 바의 칩+버튼 두 개로 표현된다. 칩은 "지금 어디 있는가"를 말하지만 "다음에 무엇을 누르면 되는가"는 말하지 않는다. 비개발자는 상태가 아니라 **행동**을 찾는다.
3. **PR의 결과(검토 중/변경 요청/반영됨/반려)**가 개발자 코멘트 패널과 피드 카드에 흩어져 있다. "내가 보낸 것이 지금 어디쯤인가"를 한눈에 보는 자리가 없다.

다섯 안은 이 세 구멍을 서로 다른 주인공으로 메운다.

## 안 1 — 「다음 할 일」: 한 버튼 수송대

**한 줄 주장**: 화면의 주인공은 대화도 미리보기도 아니라 **"지금 누르면 되는 버튼 하나"**다. git 여정 전체가 라벨이 바뀌는 단일 버튼으로 압축된다.

```
┌────────────┬──────────────────────────────────────────────┐
│ ◐ Colo  ⟨  │ ┌──────────────────────────────────────────┐ │
│ ✉ 지금 ③   │ │ 다음 할 일 — 저장하기                      │ │
│ ▸ 쇼핑몰   │ │ 고친 화면 2개가 아직 프로젝트에 담기지     │ │
│   • 대화   │ │ 않았어요. 저장하면 개발자에게 넘길 수 있음 │ │
│ ▸ 관리자   │ │              [저장하기]  [무엇이 달라졌나] │ │
│ ＋프로젝트 │ └──────────────────────────────────────────┘ │
│ ⚙          │ ┌─ 대화 ──────────────── 미리보기 ─(토글)─┐  │
│            │ │                                          │  │
│            │ │   (대화 또는 미리보기 — 한 번에 하나)     │  │
│            │ │                                          │  │
│            │ ├──────────────────────────────────────────┤  │
│            │ │ [컴포저]                                 │  │
│            │ └──────────────────────────────────────────┘  │
└────────────┴──────────────────────────────────────────────┘
```

- **현재와의 차이**: 사이클 바(칩+저장+넘기기+더 보기)가 사라지고 **「다음 할 일」 배너**가 작업 모드 머리 줄을 통째로 차지. 대화/미리보기는 나란히가 아니라 토글 — 한 번에 하나만.
- **git 여정의 모습**: `연결됨 → "만들기 시작" → "저장하기" → "개발자에게 넘기기" → "반영 기다리는 중(버튼 없음, 상태만)" → "새로 만들기"`. 사용자는 여정 내내 **같은 자리의 같은 버튼**만 누른다. 커밋·푸시·PR이 버튼 라벨 세 번의 변화로 번역된다.
- **근거**: 비개발자의 실패는 "무엇을 누를지 모르는 것"이지 "상태를 못 읽는 것"이 아니다. `deriveDelivery`가 이미 상태를 알고 있으니, 상태를 *보여주는* 대신 *행동으로 번역*해보낸다. 스테퍼가 아니라 문장+버튼이라 부활 금지 규칙에도 걸리지 않는다.
- **대가·리스크**: ① 대화/미리보기 토글은 "말하면서 화면 보기"를 끊는다 — 핀 찍기(⌥클릭)와의 상성이 최대 리스크. 완화: 핀 모드 진입 시 자동으로 미리보기 쪽으로 토글. ② "저장 안 하고 넘기기" 같은 비주류 경로는 더 보기 메뉴로 밀린다. ③ 배너가 항상 같은 자리에 있어야 효과가 있다 — 내용이 없을 때("반영 기다리는 중")도 자리를 유지하고 상태 문장만 보인다.
- **첫 화면**: 토큰 붙여넣기 직후부터 배너가 살아 있다 — "다음 할 일 — 레포 고르기". 앱의 모든 화면이 같은 질문("지금 뭘 하면 되지?")에 같은 자리에서 답한다.
- **목업**: `mockups/layout/gitflow-next-step.html`

## 안 2 — 「만들기 / 보내기」 두 개의 방

**한 줄 주장**: git은 만드는 일과 **다른 종류의 일**이다. 섞여 있으면 둘 다 어색하다 — 방을 나눈다. 보내기 방은 우체국이다: 포장하고, 보내고, 배달을 추적한다.

```
┌────────────┬──────────────────────────────────────────────┐
│ ◐ Colo  ⟨  │  보내기 — 쇼핑몰 프론트                       │
│ ┌────────┐ │  ── 보낼 것 ──────────────────────────────    │
│ │◐ 만들기│ │  ┌────────────────────────────────────────┐ │
│ │✉ 보내기│ │ │ 📦 아직 담기지 않은 변경 3건             │ │
│ │   ①    │ │ │ · 로그인 화면 — 버튼 색·문구             │ │
│ └────────┘ │ │ · 장바구니 — 빈 상태 화면                │ │
│ ▸ 쇼핑몰   │ │ · 회원 관리 — 표 여백                    │ │
│ ▸ 관리자   │ │ [이대로 저장하고 개발자에게 보내기]       │ │
│            │ │ [저장만 하기]  [치워두기]                │ │
│            │ └────────────────────────────────────────┘ │
│            │  ── 보낸 것 ──────────────────────────────    │
│            │  ● 회원 관리 화면   준호 님 검토 중 · 2시간째 │
│            │    "제목 여백만 줄여요" — 코멘트 1건   [보기] │
│            │  ● 로그인 화면      반영됨 · 어제             │
│            │  ● 배송지 목록      반려됨 · 사유 보기        │
└────────────┴──────────────────────────────────────────────┘
```

- **현재와의 차이**: 사이클 바·저장 검토 모달·넘기기 모달·개발자 코멘트 패널·저장 기록이 **한 방으로 합쳐진다**. 만들기 방은 순수해진다 — 대화+미리보기+컴포저만, 칩도 버튼도 없음. 레일 상단에 방 전환 탭 2개.
- **git 여정의 모습**: commit+push = "포장", PR = "보내기", review/merge = "배달 추적" 목록. 비개발자가 아는 유일한 git 유사 경험 — **택배** — 의 은유를 그대로 빌린다.
- **근거**: '최근에 바뀐 것들'의 절반(치워두기, 코멘트, 저장 실패 알림, 반영 지연)이 전부 "보낸 것의 추적"에 관한 것인데 표면이 흩어져 있었다. 한 방에 모으면 각각의 장치가 필요 없어진다. 프로젝트 스코프 계약도 자연스럽다 — 방 자체가 프로젝트 단위.
- **대가·리스크**: ① **저장의 순간이 만드는 순간과 분리**된다 — "방금 고친 걸 저장 안 하고 방을 나가는" 실수가 생긴다. 완화: 만들기 방에도 "담기지 않은 변경 n건" 표시는 남긴다(행동은 보내기 방에서). ② 허가 요청은 만들기 방의 일인데 사용자가 보내기 방에 있을 수 있다 — 레일 배지+방 전환 유도 필요. ③ "보낼 것"이 없으면 방이 텅 빈다 — 빈 상태를 "보낸 것" 추적만으로 채우는 설계 필요.
- **첫 화면**: 만들기 방이 기본. 보내기 방은 "담기지 않은 변경"이 처음 생기는 순간 레일에 ① 배지가 뜨면서 존재를 알린다.
- **목업**: `mockups/layout/gitflow-send-desk.html`

## 안 3 — 「프로젝트 일기」: git log를 시간축으로

**한 줄 주장**: 비개발자에게 git log는 "기록"이다. 프로젝트 홈을 **날짜순 일기**로 — 모든 사건(만듦·저장·넘김·코멘트·반영)이 한 줄의 문장으로 쌓인다.

```
┌────────────┬──────────────────────────────────────────────┐
│ ◐ Colo  ⟨  │  쇼핑몰 프론트 — 일기                          │
│ ▸ 쇼핑몰   │  ┌──────────────────────────────────────────┐ │
│ ▸ 관리자   │  │ 오늘 무엇을 만들까요?              [말하기]│ │
│ ＋프로젝트 │  └──────────────────────────────────────────┘ │
│            │  ▣ 기다리는 일 2 — 확인 요청 · 코멘트 도착     │
│            │  ── 오늘 ─────────────────────────────────    │
│            │  11:20  배송지 목록을 저장했어요               │
│            │  09:40  로그인 화면이 제품에 반영됐어요 🎉     │
│            │  09:12  준호 님이 회원 관리에 코멘트           │
│            │         "제목 여백만 줄여요"          [대화로] │
│            │  ── 어제 ────────────────────────────────    │
│            │  18:03  결제 실패 플로우를 개발자에게 넘겼어요 │
│            │  15:41  장바구니 빈 상태를 만들기 시작했어요   │
└────────────┴──────────────────────────────────────────────┘
```

- **현재와의 차이**: 피드 홈이 "나를 기다리는 일" 중심에서 **"프로젝트에 일어난 일" 시간축**으로 바뀐다. 저장 기록 모달·개발자 코멘트 패널이 일기 항목으로 흡수. 대화는 항목을 열면 펼쳐지는 딸린 기록이 된다.
- **git 여정의 모습**: commit = "저장했어요" 항목, PR = "넘겼어요", merge = "반영됐어요". git의 본질(불변의 이력)이 제품의 기억으로 번역된다 — "저번에 뭐 했더라"가 스크롤로 답된다.
- **근거**: 비개발자의 회상 단위는 시간이다 ("어제 하던 거"). 레일 트리가 이름으로 찾는 경로라면 일기는 시간으로 찾는 경로. git 용어를 하나도 쓰지 않고 git의 가치(이력·되돌리기)를 전부 노출한다.
- **대가·리스크**: ① 시간축은 **상태를 못 담는다** — "지금 검토 중"은 사건이 아니라 지속 상태라 항목 사이에 끼울 자리가 없다. 그래서 「기다리는 일」 블록이 상단에 필수 — 사실상 피드 홈의 축소판이 일기 위에 얹히는 셈(피드의 완전 대체가 아니라 병존). ② 사건이 없는 신규 프로젝트는 빈 일기 — 첫 화면이 컴포저 하나뿐. ③ 항목→대화 펼침은 대화를 2등 시민으로 만든다 — 작업은 여전히 작업 모드에서.
- **첫 화면**: 프로젝트를 열면 일기. 앱을 처음 열면 프로젝트 선택(레일) → 일기.
- **목업**: `mockups/layout/gitflow-diary.html`

## 안 4 — 「화면 보드」: 제품의 화면이 곧 목차

**한 줄 주장**: 사용자의 정신 모형은 대화도 커밋도 아니라 **"우리 앱의 화면들"**이다. 홈은 제품 화면의 섬네일 보드 — 변경·저장·넘기기가 화면에 붙는다.

```
┌────────────┬──────────────────────────────────────────────┐
│ ◐ Colo  ⟨  │  쇼핑몰 프론트 — 화면들                        │
│ ▸ 쇼핑몰   │  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │
│ ▸ 관리자   │  │ + 새   │ │┌──────┐│ │┌──────┐│ │┌──────┐│ │
│ ＋프로젝트 │  │ 화면   │ ││로그인││ ││장바구니│ │회원관리││ │
│            │  │        │ ││ [img]││ ││ [img]││ │ [img]││ │
│            │  │        │ │└──────┘│ │└──────┘│ │└──────┘│ │
│            │  │        │ │ 반영됨 │ │●저장안함│ │검토 중 ││ │
│            │  └────────┘ └────────┘ └────────┘ └────────┘ │
│            │  "장바구니"를 열면 → 그 화면의 대화+미리보기   │
│            │  저장·넘기기는 화면 카드의 메뉴가 아니라        │
│            │  상단 프로젝트 띠에 그대로 (스코프 계약 유지)   │
└────────────┴──────────────────────────────────────────────┘
```

- **현재와의 차이**: 레일의 대화 leaf 목록이 **화면 카드 그리드**로 바뀐다. 대화는 화면의 속성이 된다(한 화면 = 한 대화 스레드). 미리보기가 홈으로 올라온다 — 홈 자체가 "제품의 목차".
- **git 여정의 모습**: "로그인 화면을 고쳤고, 그 화면 카드가 '저장 안 함'을 달고, 넘기면 '검토 중'으로 바뀐다". 변경이 코드가 아니라 **화면에 귀속**되는 모습.
- **근거**: 기획자가 개발자와 말할 때의 단위가 이미 "화면"이다 ("로그인 화면요"). `ideas/화면 보드`에서 한 번 탐색된 방향을 git 여정 관점으로 재해석.
- **대가·리스크**: ① **화면↔변경이 1:1이 아니다** — 한 번의 저장이 화면 3개를 고치고, 한 화면이 대화 5개에서 고쳐진다. 카드의 상태 칩이 거짓말을 하기 시작하면 전체가 무너진다(가장 큰 리스크). ② 섬네일은 미리보기 라우트가 있어야 그릴 수 있다 — 새 화면은 아직 화면이 없다. ③ 대화 중심 작업(리팩터링, 공용 컴포넌트)은 어느 카드에도 속하지 않는다 — "화면 없는 작업" 카드가 필요해지는 순간 은유가 새기 시작.
- **첫 화면**: 프로젝트를 열면 화면 보드. 처음엔 카드가 "＋ 새 화면" 하나뿐 — 그게 첫 지시의 입구.
- **목업**: `mockups/layout/gitflow-screens.html`

## 안 5 — 「첫 사이클 마법사」: 첫 PR까지는 다른 앱

**한 줄 주장**: 토큰→첫 반영까지의 여정은 앱의 평상시 구조에 억지로 싣지 말고 **한 번만 지나가는 안내 통로**로 만든다. 첫 PR이 반영되는 순간 마법사는 해체되고 평상시 화면이 남는다.

```
┌────────────────────────────────────────────────────────────┐
│  ◐ Colo Design                                             │
│                                                            │
│        ● 연결됨   ───   ● 레포 고르기   ───   ○ 첫 화면   ───   ○ 넘기기 │
│                                                            │
│   ┌──────────────────────────────────────────────────┐    │
│   │  어떤 레포에 연결할까요?                           │    │
│   │  토큰이 볼 수 있는 레포 3개를 찾았어요             │    │
│   │                                                  │    │
```

- **현재와의 차이**: 온보딩이 "체크리스트 카드 1장"에서 **4장의 전면 화면**으로. 각 장은 결정 하나뿐: ① 토큰(왜 필요한지·어디서 구하는지 인라인 설명+붙여넣기) ② 레포 고르기 ③ 첫 화면 지시(제안 칩 3개) ④ 저장하고 넘기기(버튼 하나, "개발자에게 이렇게 보입니다" 미리보기). 완료 시 평상시 구조로 전환.
- **git 여정의 모습**: 여정 전체가 **순서 있는 4장** — 사용자는 "다음"만 누르면 첫 PR까지 도착한다. 두 번째 사이클부터는 마법사가 없고, 그때 이미 저장/넘기기를 한 번씩 해봤으니 평상시 UI가 낯설지 않다.
- **근거**: 이탈은 첫 10분에 일어난다. 평상시 구조(피드 홈+3열)는 "매일 쓰는 사람"의 최적이지 "처음 온 사람"의 최적이 아니다. 첫 사이클을 성공시키는 것이 이 질문의 절반이다.
- **대가·리스크**: ① 마법사가 가르치는 조작법과 평상시 조작법이 다르면 **배운 게 무용**이 된다 — ④의 "저장하고 넘기기"는 평상시와 같은 버튼·같은 문장이어야 함(안 1과 결합하면 해결). ② "건너뛰기"를 누른 사용자는 마법사 없이 평상시에 떨어진다 — 착지 규칙(빈 대화 시작 화면)이 받아야 함. ③ 개발자가 레포를 안 알려줬으면 ②에서 막힌다 — "레포 이름 물어보기" 안내가 필수.

## 비교와 권고

| 안 | 주인공 | git 여정의 은유 | 최대 리스크 | 구현 비용 |
|---|---|---|---|---|
| 1 다음 할 일 | 행동 버튼 | 라벨이 바뀌는 한 버튼 | 대화/미리보기 토글이 핀 찍기와 충돌 | 작음 — 배너+상태→라벨 매핑 |
| 2 두 개의 방 | 보내기 책상 | 우체국(포장·발송·추적) | 저장 순간이 만드는 순간과 분리 | 중간 — 방 라우트+목록 |
| 3 일기 | 시간축 | 기록/일기 | 지속 상태를 사건축에 못 실음 | 중간 — 사건 피드 데이터 |
| 4 화면 보드 | 제품 화면 | 화면 카드에 상태 부착 | 화면↔변경 1:1 매핑이 거짓말 | 큼 — 섬네일+매핑 |
| 5 마법사 | 여정 자체 | 4장의 안내 통로 | 배운 조작과 평상시 조작의 괴리 | 중간 — 전면 플로우 4장 |

**권고**: **1 + 5 조합**.

- 안 5가 첫 10분(토큰→첫 PR)을 책임지고, 안 1이 그 이후의 매일을 책임진다. 둘은 같은 언어를 쓴다 — "지금 누를 버튼 하나". 마법사 ④의 버튼이 평상시 배너의 버튼과 같으면 학습이 그대로 이식된다.
- 안 2는 안 1의 대안이 아니라 **확장 후보** — "보낸 것 추적" 목록이 커지면(프로젝트당 동시 PR이 3개 넘어가면) 그때 방으로 승격.
- 안 3·4는 기각이 아니라 **보류** — 둘 다 "대화가 2등 시민"이 되는 대가를 치르는데, 이 제품에서 대화는 유일한 입력 장치다. 화면 보드의 "화면에 상태 부착" 아이디어만 미리보기 도구줄의 화면 목록에 부분 채용할 가치 있음.
