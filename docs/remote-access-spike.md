# 다른 기기(폰) 접속 — 스파이크 정의와 출시 게이트

- 날짜: 2026-09-14
- 상태: **P1** (커미티 판정으로 문서 `settings-benchmark-2026-09-14.md` 의장 판정 2의 P0 을 뒤집음)
- 판정 근거는 두 위원(제품/UX · 엔지니어링/보안)이 코드를 직접 확인해 수렴한 것이다.

## 왜 P0 이 아니라 P1 인가

원안은 "기능(토큰 접속·리바인딩 동의·재발급)은 P0, QR 카드 UI 는 P1" 이었다. 그 분할선이
실제 작업량의 분할선이 아니라는 것이 코드에서 확인됐다.

| 사실 | 근거 |
| --- | --- |
| 데몬은 데스크톱 앱 안에 in-process 로 산다 — 사이드카가 없다 | `packages/desktop/src/main.ts` `new DaemonServer({ host: "127.0.0.1", port: 0 … })` |
| 페어링 토큰은 **실행마다 새로** 발급된다 — 폰에 저장한 주소는 재시작마다 죽는다 | 같은 파일의 `randomBytes(24)` |
| 이미 listen 한 서버는 다시 바인딩할 수 없다 — LAN 노출은 두 번째 listener 설계다 | `packages/daemon/src/server.ts` 의 `http.listen(port, host)` |
| 평문 HTTP 원격 origin 은 secure context 가 아니다 → 폰 브라우저에 Web Notification 이 없다 | `packages/web/src/daemon-client.ts` 의 `typeof Notification === "undefined"` 가드 |
| 가장 좁은 레이아웃 분기는 1100px 이고 작업 화면은 스플리터로 나뉜다 — 390px 은 접히는 게 아니라 깨진다 | `packages/web/src/Shell.tsx` `NARROW_QUERY`, `packages/web/src/PageWorkspace.tsx` 의 폭 계산 |

즉 "기능만 먼저"를 남기면 토큰 영속화 + LAN 리스너 + 재발급 + 동의 흐름 + 모바일 뷰가
전부 그 안에 들어온다. 게다가 알림이 없는 원격 확인은 이 기능이 팔려던 가치("자리를
비운 사이 폰으로 확인")의 절반을 잃는다.

## 스파이크가 답해야 하는 것

1. **토큰 영속화** — 페어링 토큰을 `credentials.json` 옆(OS 자격 증명 저장소)에 두고
   실행을 넘어 살릴 때, 로컬 창(`?token=`)과 원격 기기가 같은 비밀을 쓰는지, 재발급
   버튼이 기존 기기를 끊는 것이 맞는지.
2. **전송 보호(TLS)** — LAN 에 평문 HTTP + URL 쿼리 토큰은 스니핑 가능하다. 자체 서명
   인증서·mkcert·터널 중 무엇이 "기획자가 한 번의 동의로 끝내는" 경로인지.
3. **두 번째 listener** — 로컬 루프백은 그대로 두고 LAN 바인딩을 추가로 여는 설계. 동의
   없이는 절대 열리지 않아야 하고, 앱 종료와 함께 닫혀야 한다.
4. **폰 표면** — 전체 작업 화면이 아니라 **읽기 + 카드 응답 전용 뷰**(대화 읽기, 확인
   카드 응답, 질문 답하기)로 좁혔을 때 무엇이 필요한지.

## 출시 게이트 (하나라도 미달이면 기능을 켜지 않는다)

- [ ] 토큰이 재시작을 넘어 살아남고, 재발급이 한 번의 조작으로 가능하다.
- [ ] 원격 접속 경로가 TLS 로 보호된다(평문 LAN 노출 없음).
- [ ] LAN 리스너는 기획자의 명시적 동의로만 열리고, 앱과 함께 닫힌다.
- [ ] 폰 폭에서 대화 읽기와 확인 카드 응답이 실제로 동작한다(전체 작업 화면이 아니라
      이 두 가지가 기준이다).

## 지금 당장의 대체 경로

자리를 비운 기획자에게 필요한 것은 이미 데스크톱에 있다: 확인 요청·중단 알림은 즉시
가고(알림 설정과 무관), 완료 알림은 `오래 걸린 턴만` 이 기본이며, 알림을 누르면 그
대화로 바로 돌아온다. 폰 접속은 이 루프를 **대체**하는 것이 아니라 확장하는 것이므로,
게이트를 통과할 때까지 미뤄도 제품의 코어 루프는 완성된 상태다.
